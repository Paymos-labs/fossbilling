# Paymos for FOSSBilling

**English** | [简体中文](README.zh-CN.md) | [Русский](README.ru.md) | [Español](README.es.md) | [Deutsch](README.de.md) | [Türkçe](README.tr.md)

Official FOSSBilling module and payment gateway adapter (`modules/Paymos/` + `library/Payment/Adapter/Paymos/`) for [Paymos](https://paymos.io). It lets clients pay FOSSBilling invoices in four stablecoins (**USDT**, **USDC**, **USD1**, **DAI**) and gold-backed **XAUT** across 13 mainnet networks, and books confirmed payments through FOSSBilling's native billing pipeline (`addFunds` + `payInvoiceWithCredits`) across both FOSSBilling 0.7 (RedBean) and FOSSBilling 0.8+ / 2.0 (Doctrine).

## Requirements

- FOSSBilling `0.7.x` or `0.8+ / 2.0+` (`>=0.7.0 <1.0 || ^2.0`)
- PHP 8.1+ with the `pdo`, `curl`, `hash`, `json`, and `openssl` extensions
- An **HTTPS** FOSSBilling URL (`config.php` `url`) — connecting over plain HTTP is refused
- A non-empty FOSSBilling installation `salt` in `config.php`
- A Paymos account with the target project selected in the Paymos dashboard

No Composer step is required at install time: the Paymos PHP SDK (`paymos/php-sdk >= 1.11.0`) is bundled inside `modules/Paymos/vendor/`. The admin interface and checkout messages ship in six languages: English, Russian, German, Spanish, Turkish, and Simplified Chinese (`zh-Hans`).

## Install and connect

1. Download the latest release archive from [GitHub Releases](https://github.com/Paymos-labs/fossbilling/releases/latest).
2. Extract the archive over your FOSSBilling root directory — it places `modules/Paymos/` and `library/Payment/Adapter/Paymos/` in their canonical paths.
3. Open **Extensions → Overview** in FOSSBilling admin and activate the **Paymos** module.
4. Open **System → Payment Gateways → New Payment Gateway**, install **Paymos**, and enable it.
5. Open your target project in the Paymos dashboard, then navigate to **Extensions → Paymos** in FOSSBilling admin.
6. Click **Connect Paymos** and approve the binding in the Paymos tab.

Every installation downloads the same archive containing zero API keys, API secrets, project IDs, webhook secrets, or device codes. One approval provisions both **Sandbox** and **Live** environments atomically and registers the fixed Guest API callback route:

```text
https://your-billing.example/index.php?_url=/api/guest/paymos/webhook
```

After connecting, only two non-secret preferences exist: **Mode** (`Sandbox` or `Live`) and **Button Text**. No manual credential or webhook secret fields exist anywhere in the UI.

## Secret storage

Provisioned Sandbox and Live credentials and temporary RFC 8628 device flow state are sealed in authenticated AES-256-GCM envelopes (`Paymos\Plugin\AesGcmEnvelope`) keyed from FOSSBilling's `config.php` `salt` via HKDF-SHA256. Stored secrets are never rendered into HTML/Twig templates, API responses, error messages, or logs. Reconnect using **Reconnect Paymos** after changing the installation URL, revoking a Payment key, or rotating a webhook secret.

## Checkout and invoice lifecycle

- **Crash-safe creation (`STATUS_CREATING`):** Before calling `POST /v1/invoices`, the adapter persists a pending intent in `paymos_invoice_snapshots`. If the network call or process is interrupted before the response is recorded, the next invoice load replays the exact same `external_order_id`, `project_id`, `amount`, `currency`, and `environment` to recover the existing invoice without minting duplicates.
- **Line items (`products[]`):** Valid invoice lines (1–50 positive-priced items from `$invoice['lines']`) are normalized through `Paymos\Plugin\InvoicePresentation` and sent in `products[]`; invalid or empty line sets fall back cleanly to amount-only checkout.
- **Fail-closed replacement (`InvoiceReplacement`):** When an invoice total, currency, mode, or project changes — or an unpaid Paymos invoice expires (`InvoiceRenewal`) — the adapter closes the old invoice on Paymos first. If the old invoice is paid, still payable, unreachable, or returns 404, replacement is blocked (`InvoiceReplacementBlockedException`) and held for manual review so the buyer cannot pay two open invoices for the same bill. Invoices marked `paid_late_noted` also block replacement until reviewed.
- **No subscriptions:** Paymos processes push-based blockchain transfers and does not pull automatic recurring charges; renewal invoices generated by FOSSBilling are paid individually by the client.

## Webhooks and cron reconciliation

Incoming webhooks hit `/index.php?_url=/api/guest/paymos/webhook` (`Box\Mod\Paymos\Api\Guest::webhook()`), which reads the raw `php://input` body, verifies `X-Webhook-Signature` case-insensitively across both Sandbox and Live via `MultiEnvironmentWebhookVerifier` (dual-`v1=` rotation support, 300-second replay window), deduplicates atomically via `PdoEventStore` (`200` for committed duplicates, `409 Conflict` for concurrent in-flight deliveries, `401` for invalid/stale signatures), reverse-verifies terminal events with `GET /v1/invoices/{id}` (`InvoiceReverseVerifier`), enforces triangulated decimal checks (`AmountGuard`), and guards paid or finalized invoices from rollback. Non-2xx status codes (`401`/`409`/`400`/`500`) are emitted directly so `Api_Handler` never rewrites webhook errors into HTTP `200`.

`invoice.paid_late` is strictly note-only: it records `paid_late_noted` and logs a manual-review note without changing invoice payment status.

Missed webhooks are caught by the FOSSBilling cron listener (`Box\Mod\Paymos\Service::onAfterAdminCronRun` / `AfterAdminCronRunEvent`), which reconciles up to 50 unpaid Paymos invoices from the last 24 hours (throttled to once every 10 minutes) through the same verification guards and also reconciles pending and Dashboard-initiated refunds.

## Refunds and overpayments

The module implements the full Paymos refund lifecycle (`RefundCoordinator`, `RefundIntentStoreInterface`, `RefundCandidateStoreInterface`, `NativeRefundProjectorInterface`, and `RefundDiscovery`), supporting both server-calculated modes:

- **`full`:** Full refund of a paid invoice back to the verified `first_sender` address recorded by Paymos.
- **`overpayment`:** Refund of the excess amount on a `paid_over` invoice while keeping the FOSSBilling invoice paid.

Administrators with refund permissions and a valid CSRF token manage refunds under **Invoices → Paymos Refunds** (`/admin/paymos/refunds`) or via FOSSBilling 2.0's native `refundPayment()` / `listRefundsForTransaction()` adapter hooks. Arbitrary partial amounts and manual recipient addresses or networks are rejected before any API request.

- **No premature accounting debit:** Pending, processing, or unknown refunds never post a premature debit in FOSSBilling.
- **Verified completion projection:** Once `GET /v1/refunds/{withdrawal_id}` and `GET /v1/invoices/{invoice_id}` confirm `completed` (via `withdrawal.completed` webhook or cron), `full` refunds project once through FOSSBilling 2.0's `Invoice\Service::refundInvoice($invoice, $note, null, ['gateway_returned' => true, 'gateway_refund' => false, 'external_reversal' => [...]])` (with a safe FOSSBilling 0.7 fallback), while `overpayment` refunds record a completion note and leave the invoice paid.
- **Dashboard refund discovery:** Refunds initiated directly in the Paymos Dashboard or API are detected via `RefundDiscovery`, verified via signed `GET` reads, and projected without issuing a duplicate `POST /v1/refunds`.

## Troubleshooting

- **Connect refuses to start:** Verify `config.php` `url` begins with `https://` and `salt` is configured.
- **Invoice stays unpaid after payment:** Check FOSSBilling logs for `Manual review` (amount mismatch, reverse-verification conflict, or blocked replacement) or confirm the fixed webhook URL `/index.php?_url=/api/guest/paymos/webhook` is publicly reachable without HTTP auth or redirects.
- **Refund button says reconnect required:** Reconnect the installation via **Extensions → Paymos → Reconnect Paymos** so the `invoice_refunds_v1` capability is stored in the encrypted credential envelope.
